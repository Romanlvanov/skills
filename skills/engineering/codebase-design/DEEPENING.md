# Углубление

Как безопасно углубить кластер мелких модулей с учётом его зависимостей. Предполагает словарь из [SKILL.md](SKILL.md): **модуль**, **интерфейс**, **шов**, **адаптер**.

## Категории зависимостей

Оценивая кандидата на углубление, классифицируй его зависимости. Категория определяет, как углублённый модуль тестируется через свой шов.

### 1. Внутрипроцессные (in-process)

Чистые вычисления, состояние в памяти, никакого ввода-вывода. Углубляются всегда: объедини модули и тестируй напрямую через новый интерфейс. Адаптер не нужен.

### 2. Локально подменяемые (local-substitutable)

Зависимости, у которых есть локальные тестовые заменители (PGLite для Postgres, файловая система в памяти). Углубляются, если заменитель существует. Углублённый модуль тестируется с заменителем, запущенным в тестовом наборе. Шов внутренний; порта на внешнем интерфейсе модуля нет.

### 3. Удалённые, но свои (Ports & Adapters)

Твои собственные сервисы за сетевой границей (микросервисы, внутренние API). Определи на шве **порт** (интерфейс). Глубокий модуль владеет логикой; транспорт внедряется как **адаптер**. Тесты используют адаптер в памяти. Продакшен использует адаптер HTTP/gRPC/очереди.

Форма рекомендации: *«Определи порт на шве, реализуй HTTP-адаптер для продакшена и адаптер в памяти для тестов, чтобы логика жила в одном глубоком модуле, хотя он и развёрнут по сети.»*

### 4. По-настоящему внешние (Mock)

Сторонние сервисы (Stripe, Twilio и т.п.), которые ты не контролируешь. Углублённый модуль принимает внешнюю зависимость как внедрённый порт; тесты подставляют мок-адаптер.

## Дисциплина швов

- **Один адаптер означает гипотетический шов. Два адаптера означают настоящий.** Не вводи порт, если не оправданы хотя бы два адаптера (обычно продакшен + тест). Шов с одним адаптером это просто лишний уровень косвенности.
- **Внутренние швы и внешние швы.** У глубокого модуля могут быть внутренние швы (приватные для его реализации, используемые его собственными тестами), а также внешний шов на его интерфейсе. Не выставляй внутренние швы через интерфейс только потому, что их используют тесты.

## Стратегия тестирования: заменяй, а не наслаивай

- Старые юнит-тесты на мелкие модули превращаются в мусор, как только появляются тесты на интерфейсе углублённого модуля; удали их.
- Пиши новые тесты на интерфейсе углублённого модуля. **Интерфейс является поверхностью тестирования**.
- Тесты проверяют наблюдаемые результаты через интерфейс, а не внутреннее состояние.
- Тесты должны переживать внутренние рефакторинги, поскольку они описывают поведение, а не реализацию. Если тест приходится менять при изменении реализации, он тестирует в обход интерфейса.
