# Доменная документация

Как инженерным скиллам использовать доменную документацию этого репозитория при исследовании кодовой базы.

## Перед исследованием прочитай это

- **`GLOSSARY.md`** в корне репозитория, или
- **`GLOSSARY-MAP.md`** в корне репозитория, если он есть: он указывает на отдельный `GLOSSARY.md` для каждого контекста. Прочитай каждый, относящийся к теме.
- **`docs/adr/`**: прочитай ADR, затрагивающие область, в которой собираешься работать. В multi-context репозиториях проверь также `src/<context>/docs/adr/` на решения уровня контекста.

Если каких-то из этих файлов нет, **продолжай молча**. Не отмечай их отсутствие; не предлагай создать их заранее. Скилл `/domain-modeling` (к нему ведут `/grill-with-docs` и `/improve-codebase-architecture`) создаёт их лениво, когда термины или решения действительно определяются.

## Структура файлов

Single-context репозиторий (большинство репозиториев):

```
/
├── GLOSSARY.md
├── docs/adr/
│   ├── 0001-event-sourced-orders.md
│   └── 0002-postgres-for-write-model.md
└── src/
```

Multi-context репозиторий (в корне есть `GLOSSARY-MAP.md`):

```
/
├── GLOSSARY-MAP.md
├── docs/adr/                          ← system-wide decisions
└── src/
    ├── ordering/
    │   ├── GLOSSARY.md
    │   └── docs/adr/                  ← context-specific decisions
    └── billing/
        ├── GLOSSARY.md
        └── docs/adr/
```

## Используй словарь глоссария

Когда твой результат называет понятие предметной области (в заголовке задачи, предложении по рефакторингу, гипотезе, имени теста), используй термин так, как он определён в `GLOSSARY.md`. Не сползай в синонимы, которых глоссарий явно велит избегать.

Если нужного понятия в глоссарии ещё нет, это сигнал: либо ты придумываешь язык, которым проект не пользуется (передумай), либо есть настоящий пробел (отметь его для `/domain-modeling`).

## Сообщай о конфликтах с ADR

Если твой результат противоречит существующему ADR, явно скажи об этом, а не переопределяй молча:
