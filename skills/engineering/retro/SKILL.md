Пользователь попросил **ретроспективу**. Ты предлагаешь улучшения **окружения** агента-программиста, чтобы будущие запуски проходили лучше.

## Шаги

1. Вызови инструмент Skill с `writing-for-agents`, чтобы получить руководство по стилю письма.

2. Прочитай первичные источники по сессии, которую указал пользователь. Возможно, для этого придётся искать по логам сессий на этой машине. Если пользователь не указал сессию, по умолчанию бери текущую.

3. Ищи кандидатов на улучшение в следующих категориях.

- **Навигация**: насколько легко агенту было найти нужные файлы? Есть ли скрытые зависимости между файлами? Упростил бы дело **навигационный указатель**? _Применяй, когда_ сессия долго искала какую-то информацию.
- **Автоматические проверки**: есть ли автоматические проверки, которые могли бы поймать ошибки агента? Линтинг, типизация, тесты, линтеры файловой системы? Сначала прочитай собственную команду проверки репозитория (скрипты `lint`/`check` в его `package.json`/инструменте сборки, его CI-процесс), чтобы находкой стала уже существующая, но не подключённая или тихо сломанная проверка, а не её переизобретение. Репозиторий без **ограждения** (guardrail: нет pre-commit хука и нет CI-задачи, запускающей его команду lint/typecheck/test) сам по себе является находкой: репозиторий без линтинга это постоянно упускаемая возможность, а не нейтральное состояние по умолчанию. _Применяй, когда_ агент допустил ошибку, которую могла бы поймать автоматическая проверка, или в репозитории вообще нет ограждения.
- **Стандарты кодирования**: нужно ли дать **агенту-ревьюеру** новое правило для контроля? Нужно ли удалить или уточнить существующее правило? Сначала классифицируй нарушение: **механическое** (фиксированный синтаксический паттерн, запрещённый API, форма импорта, правило о расположении файла) получает детерминированную проверку, и точка: собственное правило в линтере репозитория, новый pre-commit хук или новая CI-задача, смотря что дешевле при языке репозитория и уже существующем ограждении. По умолчанию строй проверку, а не пиши правило. Оставляй `CODING_STANDARDS.md` для настоящих **вопросов суждения** (согласованность между файлами, «соответствует окружающему стилю», всё, что никакое ограждение никогда не заменит). _Применяй, когда_ агент-ревьюер не поймал ошибку.
- **Глобальный AGENTS.md**: есть ли управляющие инструкции, которые лучше перенести в стандарты кодирования (или в автоматические проверки)? _Применяй, когда_ файл AGENTS.md особенно большой, в репозитории ИЛИ в глобальной области пользователя.
- **Экономия инструментов**: делал ли агент дорогие вызовы инструментов, которые можно упростить? Есть ли собственные инструменты (CLI, MCP), особенно неэффективные по токенам? _Применяй, когда_ агент сделал дорогой вызов инструмента.
- **Пустые инструкции**: ищи в управляющих файлах инструкции, которые не меняют поведение агента. _Применяй, когда_ управляющие файлы большие и громоздкие.
- **Доступ к информации**: ищи возможности расширить доступ агента к информации. Дублирование логов dev-сервера в файл (tee), доступ только на чтение к сторонним сервисам. _Применяй, когда_ агенту была недоступна критически важная информация.

4. Покажи этих кандидатов пользователю в порядке серьёзности.

## Справка

### Реализация и ревью

Помни, что вся работа проходит две стадии: реализацию и ревью. У агента реализации самое высокое **давление на контекст**. Он отвечает за исследование, написание кода и отладку сбоев.

У агента ревью давление на контекст минимальное - он получает дифф, поэтому исследование не нужно. Ему часто не нужно писать код или отлаживать.

Значит, за соблюдение стандартов кодирования должен отвечать агент ревью, а не агент реализации.

### Файлы

В репозитории тебе доступны несколько файлов:

- `CLAUDE.md`/`AGENTS.md`: эти файлы попадают в контекстное окно любого агента, работающего в этом репозитории. Использовать их нужно крайне скупо, обычно только для **навигационных указателей** на другие файлы.
- `CODING_STANDARDS.md`: этот файл читается во время ревью, а не реализации. Добавь **навигационные указатели** на папки с документацией, если файл стандартов становится длиннее 1000 строк.
- Документация: используй документы как справочные файлы, на которые указывают другие файлы. Прежде чем писать новые документы, ищи существующие.
- Скиллы: используй скиллы для документации (поскольку их описание попадает в контекстное окно агента) или для команд, вызываемых пользователем. Следуй советам скилла `writing-for-agents`.
